## 2. 분석 방법과 확인 범위

| 구분 | 확인한 것·한계 |
|---|---|
| 원본 | 두 HTML 각 10장, 공통 CSS·JS, 일차별 계획·배포 안내 대조 |
| 실제 화면 | ego-browser에서 1920×1080 기준 20장 요소 경계 검사. 슬라이드 외곽을 넘는 요소는 발견되지 않음. 글자 내부 겹침·안전 여백까지 자동 판정한 결과는 아님 |
| 시각 검토 | 1일차 #3·#7·#9, 2일차 #1·#2·#3·#7·#8 대표 화면. 1일차 #3은 1366×768 축소 화면도 확인 |
| 도구 활용 | Sequential Thinking MCP 서버 2.0.0의 `sequentialthinking`을 로컬 stdio 연결로 5회 호출해 범위·근거·내용·구현안·완료 기준 점검. 연결 도구 목록에는 없어 기존 로컬 캐시의 서버를 직접 사용했으며 설치·설정 변경 없음 |
| 디자인 검사 | impeccable 문맥·정적 검사 활용. 허브의 작은 글자·4px 모서리 기준과 다른 값이 주로 지적됨. 발표 화면에는 별도 규격이 필요하므로 기계적 일괄 적용 제외 |
| 미확인 | Windows 실제 실행, 세 에이전트별 최신 동작, 외부 링크 접속·로그인, API별 오류 원인, 실제 프로젝터, PDF 출력 |

원본의 장점은 실습 시간과 산출물이 분명하고, 사람이 직접 입력할 인증값과 에이전트에게 맡길 지시를 구분했다는 점이다. 이 흐름은 유지한다.

## 3. 우선순위

P1은 실습 진행·이해에 영향을 주는 문제, P2는 가독성·표현 개선이다. 현재 확인한 범위에서 전체 발표를 막는 P0 결함은 없다.

| 우선 | 문제와 근거 | 수정 지시 | 완료 기준 |
|---|---|---|---|
| P1 | 2일차 #2는 `setup.ps1 실행`만 적어 단독 참여자가 실행 명령을 찾기 어려움 | 일반 PowerShell·작업 경로·실행 명령·창 재시작을 명시. 두 참여 유형의 안내는 분리 | 전날 덱 없이 설치 시작 가능 |
| P1 | 1일차 #3은 14:25–14:40 전체가 폴더 받기로 표시됨. 계획의 14:25–14:35 작업 순서·구성요소 강의가 화면에서 빠짐 | 기획 흐름·구성요소 지도 복원. 폴더 받기는 14:35–14:40 | 계획 시간과 덱의 활동이 일치 |

## 4. 공통 디자인·배치 규격

수치는 1920×1080 원본 기준의 **제안값**이다. 모바일용 재설계는 이번 범위에서 제외한다.

| 항목 | 적용 규칙 |
|---|---|
| 화면 | 1920×1080, 비율 유지 축소. 현재 `.deck`의 동작 유지 |
| 여백 | 좌우 96px, 상단 60px, 하단 최소 72px. 페이지 번호는 본문·완료 기준과 겹치지 않는 별도 위치 |
| 제목 | 일반 장 64px·900, 표지 80~84px·900. 일반 장은 제목을 왼쪽에 고정하고 시간은 오른쪽 또는 별도 행에 배치 |
| 본문 | 34~36px·400/700, 줄간격 1.4~1.5. 표·직접 입력할 명령은 32px 이상 우선 |
| 보조 글자 | 26~28px. 위치 안내 등 보조 정보만 허용. 실행에 필요한 지시를 보조 크기로 내리지 않음 |
| 강조 | 보라 `#633b86`, 짙은 잉크 `#30233e`, 흰 바탕 유지. 진한 면은 현재 실행할 지시 중심으로 제한 |
| 정보량 | 한 장에 핵심 행동 1개, 절차 3~4개 권장. 명령 2~3줄을 넘으면 설명·참고표부터 분리하고 필수 지시는 보존 |
| 2열 | 독립된 비교 또는 좌측 절차·우측 예시일 때 사용. 제목·첫 문장·패널 상단 기준선 일치. 일반 1:1, 내용상 필요하면 3:2 |
| 완료 기준 | 본문 아래 같은 위치에 `완료 기준` 제목과 1~2개 항목. 아직 수행 전인 항목을 이미 완료한 것처럼 표시하지 않음 |
| 명령 구분 | `에이전트에게`·`PowerShell`·`파일 내용`으로 용도를 명확히 표시. 현재 `.say`, `pre.cmd`를 기반으로 정리 |
| 긴 경로·코드 | 단어 전체 `nowrap`으로 공간을 밀지 않게 종류별 처리. 실제 입력 명령은 의미가 바뀌는 임의 개행 금지. 긴 오류 코드는 참고 장으로 이동 |
| 표 | 단순 비교에만 사용. 설명문이 길면 절차 장으로 전환. 열 너비와 숫자·시간 정렬을 명시 |
| 표지 | 결과물 중심의 현재 방향 유지. 긴 제목의 줄바꿈은 의미 단위로 지정. 상세 시간표와 설문 링크의 강조는 낮춤 |

| 장 유형 | 화면 구조 | 적용 예 |
|---|---|---|
| 개념 | 핵심 문장 + 간단한 관계도 + 적용 예 1개 | 기획 흐름, 일을 맡기는 3요소 |
| 실습 | 할 일 + 입력할 말 + 짧은 절차 + 완료 기준 | PRD 작성, 보고서 시작, 내 명령 만들기 |
| 비교 | 같은 높이의 열 + 비교 기준 | 참여 유형, 에이전트별 호출·저장 위치 |
| 복구 | 증상 → 확인 순서 → 대안 | API 실패, 스킬이 안 보일 때 |
| 마무리 | 결과물 확인 + 다음 행동 | 배포 후 확인, 수료 |

## 5. 1일차 슬라이드별 개선 지시

번호는 **수정 전 HTML의 section 순서이자 주소의 `#번호`**다. 장을 추가하면 번호가 바뀌므로 `aria-label`도 함께 확인한다.

| 현재 장·식별명 | 판단 | 개선 지시·권장 제목 | 완료 기준 |
|---|---|---|---|
| #1 `1일차 표지` | 결과물은 분명하나 일정·설문·도움 신호까지 한 장에 있음 | ‘내 웹앱을 만들어 / 인터넷에 올린다’ 의미 단위 줄바꿈. 결과물 2개를 주 강조. 도움 신호는 짧은 운영 안내로 | 오늘 만들 것과 마칠 시간이 먼저 보임 |
| #2 `환경설정` | 1~5 순서가 두 열로 갈림. 실행 뒤 새 창의 역할이 축약됨 | ‘설치 실행’과 ‘새 창에서 점검’ 두 장으로 분리. 다운로드 위치·일반 PowerShell·로그인·제출 위치를 배포 안내와 대조해 명시. 제출 경로는 확인 전 임의 확정 금지 | 설치 명령과 에이전트 지시를 혼동하지 않음 |
| #3 `시작 폴더 받기` | 강의 시간 누락, 준비 절차와 명령 사전이 혼합 | 앞에 ‘만드는 순서와 구성요소’ 추가. 본 장은 14:35–14:40 폴더 준비에 집중. 명령 5개는 별도 ‘오늘 쓰는 명령’ 장으로 | 경로·시킬 말·준비 완료 기준이 한눈에 들어옴 |
| #4 `PRD와 PLAN` | 완료 기준의 좋은 예가 유용. PRD·PLAN 뜻과 호출 구분이 부족 | 제목 ‘무엇을 만들고, 어떻게 확인할까’. PRD=만들 것, PLAN=만들 순서로 한 줄 정의. 자연어 호출 병기. 숫자 02는 내 주제 번호임을 유지 | PRD·PLAN 두 파일과 단계별 확인 기준을 구별 |
| #5 `화면 만들기` | 반복 작업 흐름이 있으나 서버 경로 설명이 적음 | 제목 ‘예시 데이터로 먼저 화면을 만든다’. `snapshot.json(예시 데이터) → /api/data(서버 통로) → 화면`으로 뜻 병기. 개발 서버는 켜 둔 상태로 브라우저 확인. 15:45 전환 강조 | 브라우저에서 무엇을 확인할지 PLAN과 연결 |
| #6 `실제 API 연결` | 키 보안 안내가 분명하나 키 보관이 데이터 흐름의 네 번째 상자처럼 보임 | 제목 ‘화면은 그대로, 데이터만 실제 API로’. 키 보관 안내는 흐름 밖 주의 영역으로. 키 변경 후 개발 서버 재시작 필요 여부를 시작 프로젝트 기준으로 확인해 안내 | 실제·예시 데이터 표시를 구별하고 두 상태 확인 |
| #7 `막혔을 때` | 긴 오류 코드가 눈에 띄고 조치가 한 가지 원인으로 단정됨 | 메인 장에는 오류 원문 → 가설 → 하나씩 확인과 두 번 실패 시 조교 도움. 참고표는 ‘인증 문제 / 형식 문제 / 한도 / 승인 전’ 중심으로 요약. 상세 코드는 참고 장·기존 자료로 | 오류 원인 단정 없이 확인 순서와 대안 제시 |
| #8 `디자인 다듬기와 완료 확인` | 현재는 디자인부터 지시해 남은 필수 기능과 우선순위가 모호 | 제목 ‘필수 기능 확인 후 화면 다듬기’. 남은 필수 단계 → PLAN 점검 → 시간이 남으면 디자인. 승인·한도 문제는 예시 데이터 대안 인정 | 배포 가능한 상태가 우선이며 ‘실제 데이터 필수’로 오해하지 않음 |
| #9 `배포` | 전·중·후가 한 장에 섞임 | ‘배포 전 3가지’, ‘Vercel에 올리기’, ‘공개 주소 확인’으로 분리. 환경변수 없는 사람도 예시 데이터로 진행하는 경로 명시 | 기본 주소가 열림. 키를 대화창에 입력하지 않음 |
| #10 `갤러리 등록과 마무리` | 등록·동료 확인·보안 점검·수료·내일 준비가 혼합 | ‘갤러리에 등록하고 서로 열어보기’와 ‘오늘 마무리’로 분리. 보안 확인은 배포 장에 모으고 여기서는 로그인 → 내 프로젝트 → 갤러리 순서 강조 | 갤러리 등록 후 참여 유형별 다음 행동이 보임 |

## 8. 구현 순서와 파일별 주의점

1. **P1 내용 수정 → 확인: 계획·배포 안내와 대조.** 설치 실행법, 호출 차이, 결과 파일, 빠진 강의·시연 시간을 먼저 보강한다. API 오류 조치나 외부 서비스 동작은 검증 없이 단정하지 않는다.
2. **밀집 장 분리 → 확인: 원문 조건 보존.** 각 장을 개념·실습·비교·복구·마무리 중 하나로 정리하고, 원래 번호·식별명과 새 장의 대응표를 작업 기록에 남긴다. 불필요한 장수 목표를 먼저 정하지 않는다.
3. **공통 CSS 정리 → 확인: 대표 장의 정렬·글자 크기.** `.head` 제목 기준선, 본문·완료 영역, `.cols` 상단 정렬, `code` 줄바꿈, `.done` 위계를 정리한다. 공통 CSS 수정은 양일 모두에 영향을 준다.
4. **검수·인계 → 확인: 아래 체크리스트 한 차례.** 발견한 문제를 모아 수정하고 필요한 부분만 재확인한다. 원본과 바뀐 표현을 구분해 보고한다.

| 파일 | 주의점 |
|---|---|
| `1일차.html`·`2일차.html` | 시간·완료 기준·호출 문구 우선. `aria-label`은 장의 역할을 구별할 수 있게 유지. 새 장 추가 시 마지막 장과 전체 장수 확인 |
| `deck.css` | 전체 폰트 축소로 밀도를 해결하지 않음. 인라인 margin·counter-reset은 레이아웃을 정리할 때 관련 부분만 조정. 허브 앱 CSS는 수정하지 않음 |
| `deck.js` | 현재 자동 장수·방향키·Space·PageUp/Down·Home/End·F·해시 이동 유지. 마우스 이동 버튼·새 기능은 이번 작업에 추가하지 않음 |
| 교육 계획 문서 | 이번 제안은 기존 시간 안에서 덱을 보강하는 일. 실제 일정·교육 내용을 바꾸기로 하면 전체목차 → 일차 계획 → README를 함께 맞춤 |
| 임시 자료 | 검토용 캡처·로그는 저장소 밖. 실제 키·명단·설문·수강생 화면을 예시로 넣지 않음 |

`git status`에서 이미 `.vercelignore`, `docs/04_교육운영_웹앱_기획.md` 수정과 `docs/발표자료/` 미추적 상태가 확인됐다. 기존 변경은 보존하고 후속 작업 범위를 명시한다.
